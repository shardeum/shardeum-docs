## 1. Production Deployment Best Practices

> **Production recommendation:** Run Shardeum nodes under a dedicated, non-root system user with appropriate permissions. The example paths below assume installation under `/root` and must be adjusted for your environment. **Also:** Stop any manually running node process before starting it through systemd. Never run two processes against the same node home directory.

### Using systemd Service

Create a systemd service file for automatic restarts and easier management:

```bash
sudo nano /etc/systemd/system/shardeumd.service
```

**Example service file:**

```ini
[Unit]
Description=Shardeum Node
Wants=network-online.target
After=network-online.target

[Service]
User=root
Environment="SHARDEUM_NETWORK=mainnet"
Environment="SHARDEUM_CONFIG_DIR=/root/shardeum-evm/config"
ExecStart=/root/go/bin/shardeumd start --home /root/.mainnet/node0 --chain-id shardeum_8118-1 --p2p.seeds ab6c31d63a4a30918dea8d74fb0393e5e10477c4@34.93.180.93:27656,3c722839d9745fc13df16cdfe0eb53f219a30949@34.14.143.72:27656 --p2p.laddr tcp://0.0.0.0:27656 --rpc.laddr tcp://127.0.0.1:26657 --pruning nothing
Restart=on-failure
RestartSec=3
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

Use the same node-specific start arguments and configuration described in the applicable node guide.

#### Using systemd With Cosmovisor

If the node was configured with Cosmovisor, use the following service configuration instead of the standard configuration above so the node continues to run through Cosmovisor.

Example service file:

```ini
[Unit]
Description=Shardeum Node
Wants=network-online.target
After=network-online.target

[Service]
User=root
Environment="DAEMON_NAME=shardeumd"
Environment="DAEMON_HOME=/root/.mainnet/node0"
Environment="DAEMON_ALLOW_DOWNLOAD_BINARIES=false"
Environment="DAEMON_RESTART_AFTER_UPGRADE=true"
Environment="PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/root/go/bin"
Environment="SHARDEUM_NETWORK=mainnet"
Environment="SHARDEUM_CONFIG_DIR=/root/shardeum-evm/config"
ExecStart=/root/go/bin/cosmovisor run start --home /root/.mainnet/node0 --chain-id shardeum_8118-1 --p2p.seeds ab6c31d63a4a30918dea8d74fb0393e5e10477c4@34.93.180.93:27656,3c722839d9745fc13df16cdfe0eb53f219a30949@34.14.143.72:27656 --p2p.laddr tcp://0.0.0.0:27656 --rpc.laddr tcp://127.0.0.1:26657 --pruning nothing
Restart=on-failure
RestartSec=3
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

Use the same node-specific start arguments and configuration described in the applicable node guide.

After saving the applicable service file, enable and start the service:

```bash
sudo systemctl daemon-reload
sudo systemctl enable shardeumd
sudo systemctl start shardeumd
sudo systemctl status shardeumd
```

After starting the service, check the logs and confirm that the node's latest block height is advancing:

```bash
sudo journalctl -u shardeumd -n 50 --no-pager

curl -s http://127.0.0.1:26657/status | jq -r '.result.sync_info.latest_block_height'
```

Run the block-height command again after a short interval and confirm that the height increases.

### Firewall Configuration

Before enabling UFW, allow SSH access so you do not lock yourself out of the server:

```bash
sudo ufw allow OpenSSH
```

**For Full Nodes / RPC Nodes:**

```bash
sudo ufw allow 27656/tcp   # P2P

# Only open these ports if the node is intended to provide public RPC access
sudo ufw allow 8545/tcp    # JSON-RPC
sudo ufw allow 8546/tcp    # WebSocket

sudo ufw enable
sudo ufw status
```

**For Validators:**

```bash
sudo ufw allow 27656/tcp   # P2P
sudo ufw enable
sudo ufw status
```

<Callout type="error">
Do not expose validator RPC endpoints publicly. Keep RPC access bound to localhost or restrict it to trusted internal systems.
</Callout>

## 2. Monitoring and Alerting

### Enable Prometheus Metrics

Edit `config.toml`:

```toml
[instrumentation]
prometheus = true
prometheus_listen_addr = "127.0.0.1:26660"
```

### Monitoring Stack Setup

**Recommended tools:**
- **Prometheus** - Metrics collection
- **Grafana** - Visualization dashboards
- **Alertmanager** - Alert notifications

**Key metrics to monitor:**
- Sync status
- Block height
- Validator jail status
- Disk space usage
- Memory usage
- CPU usage
- Missed blocks
- Peer count
- Network latency

### Alert Conditions

Set up alerts for:
- Node falls behind by more than 100 blocks
- Validator is jailed
- Disk usage exceeds 80%
- Memory usage exceeds 90%
- Peer count drops below 5
- Node stops producing blocks (for validators)

## 3. Security Best Practices

### Sentry Node Architecture

A recommended production setup for validators:

```
Internet → Sentry Nodes (Public) → Validator (Private IP only)
```

**Benefits:**
- Hides validator's IP address
- Absorbs DDoS traffic
- Reduces attack surface
- Improves security

**Configuration:**
1. Run validator on private network
2. Connect validator only to sentry nodes
3. Configure sentry nodes with public IPs
4. Update `persistent_peers` to point validator at sentries

### Key Management System (KMS)

For enhanced security, consider:
- **Tendermint KMS** for validator key management
- Hardware Security Modules (HSM) for key storage
- YubiHSM2 integration
- Remote signing capabilities

<Callout type="warn">
KMS setup requires advanced configuration. Thoroughly test in a non-production environment first.
</Callout>

### Security Checklist

- ✅ Use firewall rules to restrict access
- ✅ Disable SSH password authentication (use keys only)
- ✅ Keep system packages updated
- ✅ Use fail2ban or similar intrusion prevention
- ✅ Implement DDoS protection
- ✅ Regular security audits
- ✅ Monitor logs for suspicious activity
- ✅ Use VPN for administrative access

## 4. Backup and Recovery

### Critical Files to Back Up

**Validator-specific:**
```bash
~/.mainnet/$NODE_ID/config/priv_validator_key.json
~/.mainnet/$NODE_ID/data/priv_validator_state.json
```

**All nodes:**
```bash
~/.mainnet/$NODE_ID/config/node_key.json
~/.mainnet/$NODE_ID/config/config.toml
~/.mainnet/$NODE_ID/config/app.toml
```

**Wallet keys:**
```bash
# Mnemonic phrase (keep offline and secure)
```

<Callout type="warn">
**Validator backup safety:** Keep consensus keys and signing-state files secure. Never run multiple validators using the same consensus key, and do not restore an outdated `priv_validator_state.json` without verifying the latest signing state. Incorrect recovery can lead to double-signing and slashing. Use a consistent backup procedure and securely store backups offline.
</Callout>

> **Before backing up:** Stop the validator or use a tested, consistent backup procedure. Avoid copying signing-state files while they are being updated. Never restore a backup in a way that creates two active signers using the same consensus key.

### Backup Script Example

```bash
#!/bin/bash
set -euo pipefail
umask 077
NODE_ID="node0"
BACKUP_DIR="/secure/backup/location"
DATE=$(date +%Y%m%d_%H%M%S)

# Create backup directory
mkdir -p "$BACKUP_DIR/$DATE"

# Backup critical files
cp "$HOME/.mainnet/$NODE_ID/config/priv_validator_key.json" "$BACKUP_DIR/$DATE/"
cp "$HOME/.mainnet/$NODE_ID/data/priv_validator_state.json" "$BACKUP_DIR/$DATE/"
cp "$HOME/.mainnet/$NODE_ID/config/node_key.json" "$BACKUP_DIR/$DATE/"
cp "$HOME/.mainnet/$NODE_ID/config/"*.toml "$BACKUP_DIR/$DATE/"

# Create compressed archive
tar -czf "$BACKUP_DIR/backup_$DATE.tar.gz" -C "$BACKUP_DIR" "$DATE"
rm -rf -- "$BACKUP_DIR/$DATE"

echo "Backup completed: backup_$DATE.tar.gz"
```

### Disaster Recovery

**If a validator key is suspected to be compromised:**

1. Secure the affected system and prevent further unauthorized access or signing.
2. Identify whether the operator account key, consensus-signing key, or both are affected.
3. Follow the appropriate recovery procedure. Do not assume compromised consensus keys can be rotated on the existing validator.
4. Ensure the same consensus key is never active on multiple validator instances.

**If node fails:**

1. Ensure the previous validator instance is stopped and cannot resume signing.
2. Deploy a replacement server with the required configuration.
3. Restore a verified backup, including the correct consensus-signing state.
4. Synchronize the node to the current block height.
5. Verify normal operation and unjail the validator if eligible.

#### Unjailing a validator

If your validator was jailed for downtime, first resolve the underlying issue and ensure the node is syncing correctly.

Once the required jail period has expired, submit an unjail transaction using your validator operator key. Validators permanently tombstoned for double-signing cannot be unjailed.

```bash
cd "$HOME/shardeum-evm"
export SHARDEUM_NETWORK=mainnet
export SHARDEUM_CHAIN_ID=shardeum_8118-1
export SHARDEUM_CONFIG_DIR="$PWD/config"

shardeumd tx slashing unjail --from validator-key \
  --chain-id shardeum_8118-1 \
  --node tcp://127.0.0.1:26657 \
  --gas auto \
  --gas-adjustment 1.3 \
  --gas-prices 2048130280389041ashm \
  --yes
```

Replace `validator-key` if you used a different operator key name.

**To find your operator key:**

If you followed the Validator Node guide and used the default keyring configuration:

```bash
shardeumd keys list
```

If you used a custom node home or keyring backend when creating the key, specify those same settings when listing or using the key.

> **Important:** The operator account keyring and the validator's consensus-signing key are separate. Use the account key that controls your validator when submitting an unjail transaction.

## 5. Performance Optimization

### Pruning Strategies

**Full nodes (custom pruning):**
```toml
pruning = "custom"
pruning-keep-recent = "10000"
pruning-interval = "50"
```

**Archive nodes (no pruning):**
```bash
--pruning nothing
```

**Validators:**
- Use minimal pruning or default settings
- Avoid aggressive pruning to maintain full state

### State Synchronization

State sync can reduce initial synchronization time by restoring a recent network state instead of replaying the entire blockchain history.

For Shardeum v1.2.0, use a compatible post-upgrade state snapshot, if state sync is supported and suitable snapshot-serving peers are available.

Before enabling state sync, obtain two verified CometBFT RPC endpoints and a trusted block height and hash from reliable network sources.

Configure these values under `[statesync]` in `config.toml`. Do not enable state sync until the required endpoints, trusted values, and snapshot availability have been verified.

If state sync is unavailable, follow the historical binary synchronization instructions in the applicable node setup guide.

### Hardware Tuning

**SSD optimization:**
```bash
# Enable TRIM
sudo systemctl enable fstrim.timer

# Check I/O scheduler
cat /sys/block/nvme0n1/queue/scheduler
```

**Network tuning:**
```bash
# Increase network buffers
sudo sysctl -w net.core.rmem_max=134217728
sudo sysctl -w net.core.wmem_max=134217728
```

## 6. Scaling RPC Infrastructure

### Load Balancing

**For high-traffic dApps:**
- Use Nginx, HAProxy, or AWS ELB
- Run multiple RPC nodes behind a reverse proxy
- Implement rate limiting to avoid overload
- Separate "public RPC" from "private infra RPC"

**Example Nginx configuration:**

>Add the following configuration within Nginx's http context. For publicly accessible RPC services, configure HTTPS and appropriate access controls.

```nginx
limit_req_zone $binary_remote_addr zone=rpc_limit:10m rate=10r/s;

upstream rpc_backend {
    least_conn;
    server 10.0.1.10:8545;
    server 10.0.1.11:8545;
    server 10.0.1.12:8545;
}

server {
    listen 80;
    server_name rpc.example.com;

    location / {
        proxy_pass http://rpc_backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;

        # Rate limiting
        limit_req zone=rpc_limit burst=10 nodelay;
    }
}
```

### Caching Strategies

- Cache common queries (latest block, chain ID)
- Use Redis for query caching
- Implement CDN for static responses

## 8. Upgrade Procedures

### Coordinated Network Upgrades

Upgrade requirements may differ depending on whether the node is managed directly with `shardeumd` or through Cosmovisor. Always follow the release-specific instructions for the applicable network upgrade.

If your node uses Cosmovisor, add the required upgrade binary using the exact upgrade name specified for that release and continue running the node through Cosmovisor. Do not bypass the Cosmovisor-managed binary unless the release-specific instructions explicitly require it.

**Preparation:**

1. Monitor official Shardeum announcements for upgrade schedules and release-specific instructions.
2. Back up critical node files and configuration.
3. Review the release notes and upgrade requirements.
4. Confirm that the environment meets any updated requirements.

**Manual binary upgrade steps:**

1. Confirm the currently supported Shardeum mainnet release from the [official Shardeum EVM releases](https://github.com/shardeum/shardeum-evm/releases) and review any release-specific instructions.
2. Stop the node.
3. Back up the existing binary and critical node files and configuration.
4. Download the new release or Docker image.
5. Verify the provided checksum/digest.
6. Replace the existing binary/image.
7. Verify the installed version.
8. Restart the node.
9. Confirm the node is syncing and operating normally.
10. If the validator was jailed, follow the [unjail procedure](#unjailing-a-validator).

### Recovery and Rollback

Do not downgrade to an earlier binary unless the applicable release or network-upgrade instructions explicitly confirm that rollback is supported. Recovery requirements may vary between upgrades.

If an upgrade fails, first review the release-specific recovery instructions and official Shardeum announcements. If rollback is supported, restore the previous binary according to those instructions before restarting the node.

## 9. Troubleshooting Advanced Issues

### High Memory Usage

```bash
# Check memory usage
free -h
htop

# Restart node to clear memory
sudo systemctl restart shardeumd
```

### Database Corruption

Resetting node data requires the node to resync.

When a compatible snapshot is available, restore from a suitable post-upgrade snapshot.

If syncing from genesis, follow the fresh-sync instructions in the applicable node setup guide. After a state-breaking upgrade, syncing from genesis may require historical binaries and Cosmovisor to switch binaries at the appropriate upgrade heights.

<Callout type="warn">
**Caution:** Database resets can remove node state and require synchronization again. For validators, an incorrect reset or signing-state restoration can create double-signing risks. Stop the node and follow a verified recovery procedure before modifying its data directory.
</Callout>

### Network Connectivity Issues

```bash
# Test peer connectivity
telnet <peer-ip> 27656

# Check firewall
sudo ufw status verbose

# Monitor network traffic
sudo iftop -i eth0
```
