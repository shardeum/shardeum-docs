An RPC node provides JSON-RPC and WebSocket endpoints for developers, dApps, indexers, infrastructure providers, and partners. RPC nodes verify chain data but do not participate in consensus or require staking.

<Callout type="warn">
Do not expose the node's CometBFT RPC endpoint publicly. Only expose application RPC endpoints that are required for your deployment, and protect them with appropriate access controls and rate limiting.
</Callout>

## 1. System Requirements

**Recommended:**

- **OS:** Ubuntu 22.04 LTS
- **CPU:** 4 cores
- **RAM:** 8–16 GB
- **Storage:** 500 GB+ NVMe SSD
- **Network:** High-bandwidth connection
- **Dependencies:** git, jq, curl, make, build-essential, pkg-config
- **Go:** v1.25+

### Install dependencies:

```bash
sudo apt update
sudo apt install git jq curl make build-essential pkg-config -y
```

### Install Go:

```bash
curl -LO https://go.dev/dl/go1.25.0.linux-amd64.tar.gz
sudo rm -rf /usr/local/go
sudo tar -C /usr/local -xzf go1.25.0.linux-amd64.tar.gz
echo 'export PATH=$PATH:/usr/local/go/bin' >> ~/.bashrc
source ~/.bashrc
go version
```

## 2. Install Shardeum Node Binary

```bash
cd "$HOME"
git clone https://github.com/shardeum/shardeum-evm.git
cd shardeum-evm
git fetch --tags
git checkout v1.2.0
make install
```

Add the Go bin directory to PATH:

```bash
echo 'export PATH=$PATH:$HOME/go/bin' >> ~/.bashrc
source ~/.bashrc
```

Verify the installation:

```bash
shardeumd version
command -v shardeumd
```

## 3. Environment Variables

```bash
export SHARDEUM_CONFIG_DIR="$PWD/config"
export SHARDEUM_NETWORK=mainnet
export BINARY=$(command -v shardeumd)
```

## 4. Initialize the Node

```bash
NODE_ID="rpcnode"
MONIKER="shardeum-rpc"

shardeumd init "$MONIKER" \
  --chain-id shardeum_8118-1 \
  --home $HOME/.mainnet/$NODE_ID \
  --overwrite
```

## 5. Copy Genesis File

```bash
cp config/mainnet-genesis.json $HOME/.mainnet/$NODE_ID/config/genesis.json
jq -r '.chain_id' $HOME/.mainnet/$NODE_ID/config/genesis.json
```

## 6. Configure Pruning

For a typical RPC node, custom pruning helps manage storage while retaining recent state.

Edit:

`$HOME/.mainnet/$NODE_ID/config/app.toml`

Set:

```toml
pruning = "custom"
pruning-keep-recent = "10000"
pruning-interval = "50"
```

If you require complete historical state, run an Archive Node instead. Archive nodes disable pruning using `--pruning nothing`.

## 7. Enable JSON-RPC before the first start

Edit:

`$HOME/.mainnet/$NODE_ID/config/app.toml`

Under the existing `[json-rpc]` section, set:

```toml
enable = true
address = "127.0.0.1:8545"
ws-address = "127.0.0.1:8546"
```

This configuration keeps JSON-RPC and WebSocket access local to the server.

For public RPC services, use an HTTPS/WSS reverse proxy with appropriate access controls, rate limiting, and monitoring. Direct public binding requires additional security precautions.

## 8. Start and Sync the Node

### Before You Start: Syncing a New Node From Genesis After a State-Breaking Upgrade

> Skip this section if your node is already synced past upgrade height `8,390,300` or if you are restoring from a compatible post-upgrade snapshot.

For new RPC nodes, state synchronization from a compatible post-upgrade snapshot is recommended, provided suitable snapshot-serving peers and trusted RPC endpoints are available.

For state synchronization prerequisites and configuration guidance, see [State Synchronization](/docs/run-a-node/advanced-operations#state-synchronization).

The Cosmovisor instructions below are for nodes syncing from genesis.

When syncing from genesis, the node must use the binary corresponding to each part of the chain history:

- Use `v1.0.2` from genesis until upgrade height `7,927,860`.
- At height `7,927,860`, Cosmovisor switches to `v1.1.0`.
- Continue with `v1.1.0` until upgrade height `8,390,300`.
- At height `8,390,300`, Cosmovisor switches to `v1.2.0`.

Use Cosmovisor to manage both historical binary transitions automatically.

#### Set Up Cosmovisor and the Required Binaries

Install Cosmovisor:

```bash
go install cosmossdk.io/tools/cosmovisor/cmd/cosmovisor@latest

export PATH=$PATH:$HOME/go/bin

command -v cosmovisor
```

Cosmovisor uses the node's home directory to store and manage the binaries required for each part of the chain history. Set the required environment variables:

```bash
export DAEMON_NAME=shardeumd
export DAEMON_HOME="$HOME/.mainnet/$NODE_ID"
export DAEMON_ALLOW_DOWNLOAD_BINARIES=false
export DAEMON_RESTART_AFTER_UPGRADE=true
```

> Run the remaining Cosmovisor commands in the same shell session so these environment variables remain available.

Download the required Shardeum binaries from the official releases:

> **Important:** Use the current `v1.0.2` binary from the official release. An earlier `v1.0.2` binary published before October 16, 2026 cannot replay Shardeum mainnet from genesis.

```bash
mkdir -p "$HOME/shardeum-binaries"
cd "$HOME/shardeum-binaries"

curl -L \
  -o shardeumd-v1.0.2-linux-amd64 \
  https://github.com/shardeum/shardeum-evm/releases/download/v1.0.2/shardeumd-v1.0.2-linux-amd64

curl -L \
  -o shardeumd-v1.1.0-linux-amd64 \
  https://github.com/shardeum/shardeum-evm/releases/download/v1.1.0/shardeumd-v1.1.0-linux-amd64

curl -fL \
  -o shardeumd-v1.2.0-linux-amd64 \
  https://github.com/shardeum/shardeum-evm/releases/download/v1.2.0/shardeumd-v1.2.0-linux-amd64
```

Verify the SHA-256 checksums:

```bash
echo "1b57360a1d9ad340e396105521e19237cea5d162cc68eb265f00b1fe206d8849  shardeumd-v1.0.2-linux-amd64" | sha256sum -c -

echo "08cf7e6a7381bc8ffabaf265a2571304353409d85a7504f3d96fcfb0b2240f89  shardeumd-v1.1.0-linux-amd64" | sha256sum -c -

echo "909ffaf1f968a3b87a8dd6b90750fd0b285d099955dcfdf46212082fc07abc36  shardeumd-v1.2.0-linux-amd64" | sha256sum -c -
```

All three commands should return `OK`.

Make the binaries executable:

```bash
chmod +x shardeumd-v1.0.2-linux-amd64
chmod +x shardeumd-v1.1.0-linux-amd64
chmod +x shardeumd-v1.2.0-linux-amd64
```

Initialize Cosmovisor with `v1.0.2` as the genesis binary:

```bash
cosmovisor init "$HOME/shardeum-binaries/shardeumd-v1.0.2-linux-amd64"
```

Add `v1.1.0` using the exact upgrade name:

```bash
cosmovisor add-upgrade \
  v0.4.0-to-v0.6.3 \
  "$HOME/shardeum-binaries/shardeumd-v1.1.0-linux-amd64"
```

Add `v1.2.0` using its exact upgrade name:

```bash
cosmovisor add-upgrade \
  v0.6.3-to-v0.6.4 \
  "$HOME/shardeum-binaries/shardeumd-v1.2.0-linux-amd64"
```

Verify that all three binaries are in place:

```bash
"$DAEMON_HOME/cosmovisor/genesis/bin/shardeumd" version

"$DAEMON_HOME/cosmovisor/upgrades/v0.4.0-to-v0.6.3/bin/shardeumd" version


"$DAEMON_HOME/cosmovisor/upgrades/v0.6.3-to-v0.6.4/bin/shardeumd" version
```

Cosmovisor starts with `v1.0.2` and automatically switches to `v1.1.0` at height `7,927,860`, then to `v1.2.0` at height `8,390,300`, using the corresponding on-chain upgrade plans.

#### Start a Genesis Sync With Cosmovisor

If you followed the genesis-sync instructions above, start the node through Cosmovisor:

```bash
cosmovisor run start \
  --home $HOME/.mainnet/$NODE_ID \
  --chain-id shardeum_8118-1 \
  --p2p.seeds ab6c31d63a4a30918dea8d74fb0393e5e10477c4@34.93.180.93:27656,3c722839d9745fc13df16cdfe0eb53f219a30949@34.14.143.72:27656 \
  --p2p.laddr tcp://0.0.0.0:27656 \
  --rpc.laddr tcp://127.0.0.1:26657 \
  > $HOME/.mainnet/$NODE_ID/node.log &
```

### Start the Node Normally

If your node is already synced past height `8,390,300` or has been restored from a compatible post-upgrade snapshot, confirm that `shardeumd version` reports `v1.2.0` before starting the node normally.

Do not use this startup method with the current binary to sync directly from genesis.

```bash
shardeumd start \
  --home $HOME/.mainnet/$NODE_ID \
  --chain-id shardeum_8118-1 \
  --p2p.seeds ab6c31d63a4a30918dea8d74fb0393e5e10477c4@34.93.180.93:27656,3c722839d9745fc13df16cdfe0eb53f219a30949@34.14.143.72:27656 \
  --p2p.laddr tcp://0.0.0.0:27656 \
  --rpc.laddr tcp://127.0.0.1:26657 \
  > $HOME/.mainnet/$NODE_ID/node.log &
```

Monitor:

```bash
shardeumd status --home $HOME/.mainnet/$NODE_ID | jq '.SyncInfo'
```

Or

```bash
tail -f $HOME/.mainnet/$NODE_ID/node.log
```

Wait until the node is fully synced.

## 9. Optional: Enable gRPC & REST Endpoints

Edit:

`$HOME/.mainnet/$NODE_ID/config/app.toml`

Under the existing `[grpc]` section, set:

```toml
enable = true
address = "127.0.0.1:9090"
```

Under the existing `[api]` section, set:

```toml
enable = true
address = "tcp://127.0.0.1:1317"
```

Enable these only if required by your infrastructure. Restart the node after making changes.

> These endpoints are bound to localhost by default. For external access, expose them through trusted infrastructure with appropriate network restrictions and security controls.

## 10. Firewall Configuration

Before enabling UFW, allow SSH access so you do not lock yourself out of the server:

```bash
sudo ufw allow OpenSSH
```

Allow P2P traffic:

```bash
sudo ufw allow 27656/tcp
```

If JSON-RPC or WebSocket services are intentionally bound to an externally reachable interface, allow only the ports required for your deployment:

```bash
sudo ufw allow 8545/tcp   # JSON-RPC
sudo ufw allow 8546/tcp   # WebSocket
```

For production deployments using a reverse proxy, expose the proxy's HTTPS port instead and keep backend RPC ports restricted.

The optional gRPC and REST endpoints are bound to localhost in this guide, so their ports do not need to be opened publicly.

If external access is required, configure the appropriate network binding and restrict access to trusted systems or private networks. Avoid exposing these endpoints directly to the public internet.

After configuring the required firewall rules, enable UFW and verify its status:

```bash
sudo ufw enable
sudo ufw status
```

<Callout type="error">
Do not expose port `26657` (CometBFT RPC) publicly. Restrict sensitive endpoints to localhost or trusted systems, and protect public RPC endpoints with suitable rate limiting and reverse-proxy controls.
</Callout>

## 11. Run as a systemd Service (Recommended)

For production RPC infrastructure, use systemd to manage automatic startup, process recovery, and centralized logging.

See [Using systemd Service](/docs/run-a-node/advanced-operations#using-systemd-service) for configurations covering both direct `shardeumd` execution and Cosmovisor.

When adapting the examples for your RPC node:

- Replace the example node home `/root/.mainnet/node0` with `/root/.mainnet/rpcnode`.
- Use the correct binary paths, system user, and environment variables.
- Follow the RPC configuration and startup settings established in this guide.
- Use a distinct service name and non-conflicting ports if running multiple nodes on the same server.

> **Important:** Stop any manually running node process before starting it through systemd. Never run two processes against the same node home directory.

After starting the service, verify that the node's block height is advancing and that the required RPC endpoints are responding.

## 12. Scaling RPC Nodes (Optional)

For high-traffic dApps:

- Use load balancers such as Nginx, HAProxy, or AWS ELB
- Run multiple RPC nodes behind a reverse proxy
- Rate-limit requests to avoid overload
- Separate public RPC from private infrastructure RPC
- Run dedicated indexing services in parallel where required

## 13. Useful Commands

**Check sync:**

```bash
shardeumd status --home $HOME/.mainnet/$NODE_ID | jq '.SyncInfo'
```

**Check network peers:**

```bash
curl -s http://localhost:26657/net_info | jq '.result'
```
**Check logs:**

Use the systemd service name configured for your node. The Advanced Operations example uses `shardeumd`. If you created a separate service such as `shardeumd-rpc`, use that name instead.

```bash
journalctl -u shardeumd -f
```

**Query RPC:**

```bash
curl -s http://localhost:8545 \
  -X POST \
  -H "Content-Type: application/json" \
  --data '{"jsonrpc":"2.0","method":"eth_blockNumber","params":[],"id":1}'
```

**Verify the EVM chain ID:**

```bash
curl -s http://127.0.0.1:8545 \
  -H "Content-Type: application/json" \
  --data '{"jsonrpc":"2.0","method":"eth_chainId","params":[],"id":1}'
```

Expected chain ID: `0x1fb6` (8118).

**Check synchronization health:**

```bash
curl -s http://127.0.0.1:26657/status \
  | jq -r '.result.sync_info.latest_block_height'
```

Confirm that the block height continues advancing and approaches the latest mainnet height.

> **Important:** An RPC endpoint responding successfully does not guarantee that the node is processing new blocks. Always verify block-height progression after an upgrade.

## 14. Troubleshooting

### RPC endpoint not responding

- Confirm RPC enabled in `app.toml`
- Confirm IP binding is correct
- Check firewall rules
- Check node is fully synced

### High latency

- Check CPU, memory, disk I/O, and network utilization
- Review RPC request volume and rate limits
- Confirm the node remains fully synced
- Scale across additional RPC nodes if required

### Node stuck catching up

- Check peers
- Restart node
- Verify time sync (NTP)
- If syncing from genesis, verify that Cosmovisor is configured with all three historical binaries and both upgrade plans.
- Verify the expected binary version for the node's current block height.
- If errors such as `auth failure` or `wrong Block.Header.AppHash` occur, inspect peer connections, binary checksums, and node logs. If unresolved, share the relevant logs in the [validator support channel](https://discord.com/channels/933959587462254612/1354796083066179614).
